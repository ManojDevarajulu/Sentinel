The problem

AI agents write code faster than humans can understand it

Cursor, Claude Code, and GitHub Copilot generate hundreds of lines per session. Developers ship it without knowing which other files depend on what just changed. One PR touches lib/supabase/client.ts and silently breaks auth in middleware 3 hops away. Nobody finds out until production is down.

The solution

Sentinel maps your codebase as a dependency graph and computes blast radius on every PR

It parses your TypeScript/Next.js repo using your own MIT-licensed AST engine (built with typescript-estree), stores the graph in Supabase, and runs a reverse BFS traversal every time a PR is opened. The result appears as a GitHub PR comment in under 3 seconds — showing risk level, affected file count, and critical paths. Teams that use it stop shipping broken PRs.

All features

Ordered by build priority. Phase tells you when it ships.

Phase 1 — Core engine

🔍

AST Dependency Parser P1

Parses every .ts/.tsx file in the repo using typescript-estree. Extracts all imports, exports, function calls, React component usage, Next.js route structure, and Supabase RPC calls. Outputs a full adjacency list stored in Supabase. Runs on first connect and on every webhook push.

💥

Blast Radius Computation P1

Reverse BFS from changed files. Finds every node reachable within 4 hops. Returns affected count, risk level (Low/Medium/High), risk score 0–100, and critical paths. Runs in under 800ms on a 1,000-node repo.

⚡

GitHub Action + PR Comment P1

Installs in 60 seconds. Posts a formatted comment on every PR with risk badge, affected file count, top 5 critical affected files with paths, and link to dashboard. Free forever. Published on GitHub Marketplace.

Interactive Dependency Graph P2

Optional GitHub status check that blocks PR merge if blast radius risk exceeds a configurable threshold. Teams set their own rules: "never merge if middleware.ts is in blast radius without 2 approvals." Enterprise feature.

Tech stack

Parser engine — you own this entirely

typescript-estree

AST Parser

MIT licensed. From the TypeScript-ESLint team. Parses every .ts/.tsx file into an AST you walk to extract imports, exports, JSX components, function calls. This is the foundation. Zero AGPL.

Bun runtime

3x faster than Node.js for file I/O. Critical when scanning 500+ file repos. Runs in the GitHub Action container and on your backend as a sidecar process.

Custom BFS engine

Build phases

14 weeks total. Designed for 2–3 coding hours on weekdays + both days of 2 weekends/month.

PHASE 01 The engine — parser + blast radius API Weeks 1–3 · ~60 hrs

The foundation everything else is built on. No UI, no auth, no billing. Just make the parser work and the BFS algorithm correct.

AST parser script — Bun script using typescript-estree. Input: repo path. Output: JSON adjacency list {node_id, file_path, type, imports[], exports[]}. Target Next.js app router conventions first.

Node type classifier — Detect: page, layout, component, hook, api_route, middleware, util, supabase_client. Used later for criticality scoring.

Reverse BFS function — Pure Python function, no DB yet. Takes adjacency dict + starting node IDs. Returns all reachable nodes with hop distance. Unit test this heavily.

FastAPI skeleton — POST /repos/scan and GET /blast-radius. No auth. Test locally with curl. Store graph in Supabase (manual setup).

Risk scorer — Given affected nodes, compute risk score 0–100 and risk level. Middleware in blast radius = instant HIGH. Tune thresholds on your own codebase.

✓ Milestone: Parser runs on your own repo and produces a correct graph. BFS returns the right affected files for a known change.
